# Telemost X — матрица возможностей и блокеров

**Состояние на:** 2026-11-13
**Область:** текущий исходный код приложения и уже сохранённые исследования.
Новых сетевых экспериментов, OAuth-запросов или обращений к внутренним
endpoint’ам не проводилось.

## Матрица

|---|---|---|---|---|
| **Авторизация** | В приложении есть только интерфейс `SessionRepository.hasActiveSession()`; реализации входа нет. Статическое исследование оригинального приложения выявило Passport Activity, получение OAuth-токена и внутренний `request_user`/XivaSecret flow, но не разрешение использовать его стороннему клиенту. Официальный REST OAuth покрывает встречи/настройки для бизнес-домена; MCP использует OAuth от имени пользователя, но остаётся интерфейсом внешнего агента. См. Внутренний flow исходного приложения не является публичным контрактом. | **Да, частично:** модель состояния сессии, экран входа/ошибок и границу хранилища учётных данных можно спроектировать отдельно. Реальный вход и сохранение действующих токенов — нет. | Описать состояния сессии и проверить их локальными тестами. Для настоящего входа запросить у Яндекса документированный путь регистрации и права именно для клиентской переписки; не использовать `request_user` как сторонний API. |
| **Список чатов** | Официальный MCP документирует `list_chats`, `search_chats`, `get_chat` для чатов, доступных авторизованному пользователю. Опубликованный REST-каталог Telemost не содержит общего метода списка чатов. В приложении нет chat-list UI или источника данных. См. Локальные тестовые данные не должны выдаваться за реальные чаты. | Проверить UI и сортировку на локальных fixtures. До подключения определить разрешённый источник списка и получить его формальный контракт. |
| **История сообщений** | MCP документирует чтение истории чата и треда, отдельных сообщений и поиск (`list_chat_messages`, `list_thread_messages`, `get_chat_message`, `get_thread_message`, `search_messages`), только в доступных аккаунту чатах. В оригинальном приложении статически найдены `HistoryRequest` и обработка history responses. В Telemost X есть только модель `ChatMessage` и сигнатура `loadMessages`, без реализации транспорта. См. [MCP capabilities](./mcp-capabilities.md), [HistoryRequest research](../../research/logs/protocol-stage-45.log), [message model](../../TelemostX/TelemostX/app/src/main/java/ru/deabolus/telemostx/core/model/ChatMessage.kt), [transport interface](../../TelemostX/TelemostX/app/src/main/java/ru/deabolus/telemostx/core/transport/TelemostTransport.kt). | MCP не публикует схемы параметров, точный формат пагинации или гарантию полного экспорта; полнота зависит от просмотренных страниц и условий поиска. Не подтверждён поддерживаемый history API для прямого native-клиента. | **Да:** лента, форматирование, группировка, хронологическая сортировка и локальное представление уже имеющих форму сообщений. | Проверить ленту на локальных fixtures: порядок, пустые/ошибочные состояния и длинные сообщения. Перед сетевой реализацией получить документированный контракт источника и пагинации. |
| **Получение новых сообщений** | MCP перечисляет поиск и чтение истории, но не инструмент подписки на новые сообщения или push-события. Исследования оригинального клиента описывают Xiva/WebSocket push, MessagePack и reconnect — это статическое исследование внутреннего протокола, не разрешение на его использование. В приложении нет listener/sync реализации. См. [MCP capabilities](./mcp-capabilities.md), [WebSocket findings](../../research/logs/protocol-stage-58.log), [push/reconnect findings](../../research/logs/protocol-stage-59.log), [message transport](../../research/logs/protocol-stage-60.log). | Нет подтверждённого публичного real-time интерфейса, cursor/`since` контракта, задержки или гарантий дедупликации. Повторный MCP-поиск может обнаружить сообщения, но не является документированной гарантированной доставкой. | **Да:** можно сделать независимый алгоритм объединения страниц, дедупликации по абстрактному ID и вычисления непрочитанного счётчика; сетевую синхронизацию пока не подключать. | Реализовать и локально протестировать merge/dedup на искусственных наборах. До получения источника новых событий не объявлять polling или Xiva рабочим способом доставки. |
| **Отправка сообщений** | Официальный MCP прямо ограничивает чаты режимом чтения и запрещает отправку/изменение/удаление сообщений. В оригинальном приложении исследованы внутренние send directives и `PostMessage`-ответы. В Telemost X `sendMessage` существует только как абстрактная сигнатура `TelemostTransport`; реализации нет. См. [MCP capabilities](./mcp-capabilities.md), [send flow research](../../research/logs/protocol-stage-44.log), [send response research](../../research/logs/protocol-stage-49.log), [transport interface](../../TelemostX/TelemostX/app/src/main/java/ru/deabolus/telemostx/core/transport/TelemostTransport.kt). | Не найден публичный поддерживаемый метод отправки чат-сообщений для стороннего клиента, scope, формат подтверждения или правила идемпотентности/повторов. MCP не может служить транспортом отправки. | **Да, частично:** композер, локальные черновики, валидация текста и состояния UI можно сделать без сети. Состояние «доставлено» или реальная очередь отправки — нельзя подтвердить. | Проверить композер и модель черновика локально. Для отправки запросить у Яндекса официальный write API/SDK и разрешённые права; только после этого планировать авторизованный интеграционный тест. |
| **ReadMarker и SeenMarker** | В оригинальном приложении найдены внутренние `ReadMarker`, `SeenMarker`, `SeenMarkerEntity`, очередь/сохранение и связанные поля чата. В Telemost X есть локальная модель предпочтений приватности и интерфейс `markRead`, но они не подключены к сети. MCP запрещает менять состояние прочтения. См. Нельзя обещать, что локальная настройка остановит серверную отметку; эффект чтения через MCP на read/unread-состояние также не подтверждён. | **Да:** локальные настройки, текст объяснения и pure policy/state logic можно реализовать; они будут управлять только поведением клиента, пока нет поддерживаемого транспорта. | Добавить локальные тесты политики и UX, явно не называя их серверным подавлением. Нельзя считать, что отключение heartbeat или локальный toggle скрывает статус; публичный REST/MCP-контракт такого переключателя не документирует. | **Да, частично:** экран настройки, локальное сохранение выбора и честное описание ограничений не зависят от сервера. ## Компоненты, независимые от сетевой авторизации

Можно начинать или продолжать отдельно, не выдавая локальное поведение за
работающую интеграцию:

1. **UI и навигация:** список чатов и экран переписки как представления
   абстрактных моделей; loading/empty/error states, доступность и тема.
2. **Локальные модели:** `ChatSummary`, `ChatMessage`, пользователь,
   черновик/состояние отправки и локальные настройки. `ChatMessage` уже есть;
   поля протокола не добавлять без подтверждённого контракта.
3. **Чистая доменная логика:** сортировка и отображение истории, объединение
   страниц, дедупликация по абстрактному стабильному ID, форматирование дат.
   Серверный cursor и гарантию доставки не предполагать.
4. **Локальная приватность:** экран предпочтений, объяснение их фактической
   области действия, настройки и тесты. До разрешённого протокола это только
   локальные предпочтения, не подавление серверных маркеров/presence.
5. **Локальные черновики и хранилище:** схема, миграции, retention и обработка
   удаления пользовательских данных. Секреты и реальные токены в fixtures,
   тестовых ресурсах и репозитории не помещать.
6. **Тестирование без сервера:** unit/UI-тесты для моделей, reducer/state
   transitions, сортировки, дедупликации, настроек и экранных состояний.
   Локальные fixtures являются тестовыми данными, а не сетевыми результатами.
7. **Архитектурные границы:** развивать существующие интерфейсы
   `SessionRepository`/`TelemostTransport` и локальные реализации только для
   неавторизуемых функций; сетевой адаптер оставить отсутствующим, пока нет
   допустимого контракта.
